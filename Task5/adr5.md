# ADR-5: Мультитенантная SaaS-платформа мониторинга скота


**Дата:** 2026-11-22
**Связан с:** ADR-4 (выбран вариант локальной арзитектуры), ADR-2 (ограниченные контексты), ADR-3 (детализация пайплайна CV)
**Автор:** Друзин Н.С.


## Контекст

MVP на основе локальной архитектуры успешно внедрён на собственных фермах «АгроТех Х» (см. ADR-4).
Бизнес решил вывести решение как SaaS-платформу для других агрохолдингов. Это меняет модель деплоя:
изолированная система одной компании превращается в мультитенантную платформу с облаком в центре.


## Драйверы решения (требования к SaaS)

- Полная изоляция данных между клиентами (данные о поголовье — коммерческая тайна).
- Гибкие тарифы и биллинг, интеграция с российскими платёжными системами.
- Открытый API для интеграций + dev-портал для самостоятельного онбординга.
- Панель самообслуживания (админ-интерфейс на этапе MVP не требуется).
- Горизонтальное масштабирование по мере роста числа клиентов.
- Сбор метрик использования для аналитики и биллинга.


## Задача 1. Изоляция данных: рассмотренные варианты

| Критерий | A. Общая БД + `tenant_id` (RLS) | B. Схема на клиента (+ RLS) | C. Инстанс на клиента |
|---|---|---|---|
| Изоляция данных | Средняя (логическая) | Высокая (схемы + RLS) | Максимальная (физическая) |
| Стоимость на клиента | Минимальная | Низкая | Высокая |
| Операционная сложность | Низкая | Средняя (миграции N схем) | Высокая (N инстансов) |
| Шумные соседи | Возможны | Возможны (управляемо) | Исключены |
| Скорость онбординга | Минуты | Минуты (миграция шаблона схемы) | Часы–дни |
| Кастомизация под клиента | Ограничена | Средняя | Полная |
| Путь для enterprise-клиентов | Слабый | Хорошая опция апгрейда | Естественный вариант |

**Решение: гибридный вариант B как базовый.**
- Базовые клиенты — отдельная схема в общей PostgreSQL + Row-Level Security, события — партиции по `tenant_id` в ClickHouse, видео — префиксы `tenant/{id}/` в S3.
- Крупные/enterprise-клиенты (по желанию или тарифу) — отдельная БД, при необходимости отдельный инстанс.
- Мультиарендность пронизывает все контексты из ADR-2: каждый сервис включает `tenant_id` в контракт (MQTT-топики `tenant/{id}/...`, JWT-клеймы, ключи шифрования S3).

**Компромиссы:** гибридная изоляция усложняет миграции (инструмент батч-миграций обязателен); RLS требует дисциплины подключения «от имени тенанта»; enterprise-инстансы увеличивают стоимость эксплуатации — принимается осознанно, вынесено в тарифы.

## Задача 2. Биллинг и монетизация

- **Сервси тарифов** — тарифные планы (по числу ферм, камер, объёму событий и хранения).
- **Сревис метрик** — счётчики использования (камеры, события CV, объём видео, API-вызовы) собирает из ClickHouse/очередей; итоги раз в сутки пишет в биллинг.
- **Сервис Биллинг** — расчёт по тарифу, периоды, счета, просрочки. Отдельная схема `billing` в PostgreSQL.
- **Платежный шлюз** — интеграция с ЮKassa (карты, СБП), выставление счетов и вебхуки о платежах; для B2B дополнительно — счета на оплату и закрывающие документы.
- Монетизация: подписка + overage за превышение лимитов события/хранения.


## Задача 3. Интеграции с клиентами

- **Шлюзз APi** (Kong/APISIX): OpenAPI 3.0, аутентификация — API-ключи и OAuth2 Client Credentials, rate limits на тенанта.
- **Границы публичного API v1:** события мониторинга (уведомления), метрики поголовья, статусы оборудования, вебхуки (обратная доставка событий клиенту). Управление фермами и агентами — только через панель самообслуживания.
- **Dev-портал:** документация по OpenAPI, sandbox-тенант с демо-данными, коллекция примеров (Postman), выпуск/ротация ключей в личном кабинете.
- Edge-агенты подключаются по протоколу, унаследованному из MVP (MQTT over TLS, store-and-forward) — тенант регистрирует фермы и получает креды агентов в панели.


## Задача 4. To-Be архитектура

Финальные диаграммы C1 и C2 — файлы `C1_saas_final.puml`, `C2_saas_final.puml`.
Пример интеграции с «АгроТех Х» как клиентом платформы — `C2_integration_example.puml`.
Варианты изоляции — `C2_isolation_schema.puml`, `C2_isolation_db.puml`, `C2_isolation_instance.puml`.


## Риски

| Риск | Мигрирование |
|---|---|
| Утечка данных между тенантами | RLS + тесты изоляции + аудит запросов |
| Дорогие миграции N схем | Единый инструмент миграций (Flyway/Liquibase) |
| Зависимость от одного платёжного провайдера | Абстракция Платежный шлюз, второй провайдер как запасной |
| Пики видеонагрузки новых клиентов | Квоты на GPU-инференс, планирование мощностей |
| Отсутствие админ-интерфейса | Операции поддержки через IaC/SQL-скрипты, временно |
